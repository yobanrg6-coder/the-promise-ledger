# Forecast Ledger

The falsifiable-prediction subsystem behind TopicAhead's "Attention Intelligence Layer" claim. Zero LLM calls — pure deterministic scoring (`agents/scoring.py`) + real HTTP pulls against Google Trends. Free to run unattended, and its accuracy number can't be an invented claim because nothing here is generated by a model.

## How a prediction is made and resolved

1. `predictor.make_predictions_for_market_pair(baseline_geo, target_geo)` pulls both markets' real daily trending lists, finds topics trending in `baseline_geo` but **not yet visible** in `target_geo` (`agents/scoring.py::find_cross_market_gaps`), and keeps only candidates that pass two grounded filters:
   - `velocity >= MIN_VELOCITY_TO_PREDICT` (8) — a real traffic/rank-derived score, not an LLM guess.
   - `related_news_count >= MIN_RELATED_NEWS_TO_PREDICT` (1) — added 16-ago-2026. A candidate backed by zero real news articles is usually a bare name spike (a specific athlete, a local fixture) with no realistic path to another country's own top-10 list. The first live batch without this filter (90 predictions, all bare name spikes) resolved at a genuine 0% accuracy.
2. The top `MAX_NEW_CANDIDATES_PER_MARKET_PAIR` (3) surviving candidates each get a falsifiable prediction recorded at **1h, 4h, 12h and 24h** horizons: *"topic X will appear in target_geo's own trending list within N hours."*
3. `predictor.resolve_due_predictions()` re-pulls `target_geo`'s trending list once the horizon elapses and checks for a real match. If the fetch itself fails or returns nothing (network hiccup, feed unreachable), the prediction is **left PENDING and retried next cycle** — it is never resolved as INCORRECT just because a check failed. Conflating "didn't happen" with "couldn't check" would silently poison the accuracy stat on every transient outage during the unattended 6h cycle; this distinction was added 16-ago-2026 after finding the original code did exactly that.

## Running it

- One-off: `python -m ledger.run_cycle` (or `venv\Scripts\python.exe -m ledger.run_cycle` on Windows).
- Unattended: `ledger/run_cycle.bat` wired to the Windows Scheduled Task `TopicAheadLedgerCycle`, firing every 6h. Requires the machine's Windows session to be logged in (`LogonType: Interactive`) — it does **not** need an active Claude/dev session. As of 16-ago-2026 its power settings (`DisallowStartIfOnBatteries` / `StopIfGoingOnBatteries`) are both `False`, so a cycle no longer gets silently skipped while running on battery.
- Logs to `data/ledger_cycle.log`. `get_forecast_accuracy()` (exposed as an MCP tool) returns the live totals.

## Known limitation

A 1-24h window for a topic to cross from one country's fixed 10-slot trending list into another's is inherently a hard bet — most real predictions will still resolve INCORRECT even with good candidate selection. `accuracy_pct` is `null` until at least one prediction has been evaluated, and is never padded or estimated — see `store.get_accuracy_stats()`.
