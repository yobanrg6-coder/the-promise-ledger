# Forecast Ledger

The falsifiable-prediction subsystem behind The Promise Ledger's "Attention Intelligence Layer" claim. Zero LLM calls — pure deterministic scoring (`agents/scoring.py`) + real HTTP pulls against Google Trends. Free to run unattended, and its accuracy number can't be an invented claim because nothing here is generated by a model.

## Redesigned 26-ago-2026 — read this before touching resolution logic

The original design (one prediction per fixed `baseline_geo -> target_geo` pair, resolved by a single "did it crack the target's own top-10" check) ran for 9 days in production and resolved 2,388 predictions at **0.08% real accuracy** (2 correct). Root cause: a country's own 10-slot daily trending list is dominated by sports/local content that structurally never crosses borders, so the bar was nearly unreachable regardless of candidate quality. The fix has two parts, both live:

1. **Widen the claim (Cloud Run, no new dependency).** `predictor.make_predictions_for_baseline(baseline_geo, target_geos)` predicts "will appear in **at least one** of several tracked markets" instead of one fixed pair (`agents/scoring.py::find_multi_target_gaps`). Same real, exact, zero-LLM methodology, just more real chances per bet.
2. **A graded second opinion for near-misses, off Cloud Run.** A topic can gain real search traction in a market without literally out-ranking that market's own top-10 obsessions. `trends_service.py::fetch_relative_search_ratio` checks that via a real, comparative pytrends query (a topic compared against a market's own weakest *currently confirmed trending* item, in the same payload — a lone keyword self-normalizes to 100 regardless of true volume, verified live with a Mexico-only welfare program hitting "100" in the US, so this can never be a single-keyword threshold). **This step cannot run on Cloud Run** — Google reliably blocks/rate-limits it from Cloud Run's own egress IPs (verified live 26-ago-2026: a real 45-second cooldown retry still got HTTP 429). It runs instead from `ledger/run_graded_check_relay.py`, meant to be triggered periodically from a normal, non-datacenter machine.

## How a prediction is made and resolved (current flow)

1. **`run_cycle.py`** (Cloud Run, every 6h) calls `predictor.make_predictions_for_baseline(baseline_geo, target_geos)` once per tracked market (`GEOS = ["US", "MX", "ES", "GB"]`, each baseline's targets are the other three). Candidates must pass the same two grounded filters as before:
   - `velocity >= MIN_VELOCITY_TO_PREDICT` (8) — a real traffic/rank-derived score, not an LLM guess.
   - `related_news_count >= MIN_RELATED_NEWS_TO_PREDICT` (1) — added 16-ago-2026. A candidate backed by zero real news articles is usually a bare name spike (a specific athlete, a local fixture) with no realistic path to any tracked market's top-10. The first live batch without this filter (90 predictions, all bare name spikes) resolved at a genuine 0% accuracy.
   - The top `MAX_NEW_CANDIDATES_PER_BASELINE` (3) surviving candidates each get a falsifiable prediction at **1h, 4h, 12h and 24h** horizons: *"topic X will appear in at least one of target_geos' own trending lists within N hours."*
2. **`run_cycle.py`** also calls `predictor.resolve_due_predictions()` first, every cycle. This is the **free, exact-match-only half** — no pytrends call, ever, from Cloud Run. For each due prediction it checks every tracked target for a real top-10 match:
   - Match found in any target → **CORRECT**, final.
   - No fetch succeeded for any target → left **PENDING**, retried next cycle (couldn't check ≠ didn't happen — this distinction was added 16-ago-2026 after finding the original code conflated a network hiccup with a real miss).
   - Every target fetched fine but none matched → handed to **`NEEDS_GRADED_CHECK`** (`store.mark_needs_graded_check`) — a real, high bar cleared "confirmed absent everywhere right now", but that's still not proof of "wrong".
3. **`run_graded_check_relay.py`** (run from a normal IP, e.g. this machine via Task Scheduler) calls `predictor.resolve_needs_graded_check()`, which for each `NEEDS_GRADED_CHECK` item: re-checks for a late exact top-10 match (free), then falls back to the comparative `fetch_relative_search_ratio` signal against each target's own weakest trending item, keeping the best result across all tracked targets. Clears the bar (`RELATIVE_SIGNAL_THRESHOLD`, currently 0.25 — a provisional calibration, see the constant's own comment in `predictor.py`) → **CORRECT**. Doesn't → **INCORRECT**, final. If pytrends itself is unreachable this run → stays `NEEDS_GRADED_CHECK`, retried on the relay's next run.

Predictions recorded before 26-ago-2026 still carry a singular `target_geo` field instead of `target_geos` — both `resolve_due_predictions` and `resolve_needs_graded_check` handle either shape uniformly (`prediction.get("target_geos") or [prediction["target_geo"]]`), no data migration needed.

## Storage

Predictions are stored in **Firestore** (`predictions` collection, project `topicahead-hackathon`) in production, behind the `PredictionBackend` protocol in `store.py`. Tests run against `InMemoryBackend` (no network, no emulator). The original implementation used a local SQLite file (`data/ledger.db`), replaced 17-ago-2026 because Cloud Run's per-instance filesystem is ephemeral — a restart or scale-to-zero would have silently wiped every accumulated prediction. `data/ledger.db` still exists in the repo as a historical snapshot from before the migration; nothing reads it anymore.

## Running it

- One-off, local: `python -m ledger.run_cycle` (needs `GOOGLE_APPLICATION_DEFAULT` credentials for the `topicahead-hackathon` project, or run it from Cloud Shell / a machine already authenticated to that project).
- Unattended, production (exact-match half): **Cloud Run Job `ledger-cycle`** (same container image as the web service, entrypoint overridden to `python -m ledger.run_cycle`; no Gemini key needed — the ledger cycle never calls an LLM), triggered every 6h by **Cloud Scheduler job `ledger-cycle-scheduler`** (`0 */6 * * *` UTC) via an authenticated REST call to the Cloud Run Jobs API.
- Unattended, local (graded-check half): `python -m ledger.run_graded_check_relay`, triggered periodically (Windows Task Scheduler on this machine) — **must not run on Cloud Run**, see the "Redesigned" section above for why.
- `get_forecast_accuracy()` (exposed as an MCP tool) returns the live totals straight from Firestore, now including a `needs_graded_check` count alongside `pending`/`correct`/`incorrect` (see `store.get_accuracy_stats()`).

## Known limitation

A 1-24h window for a topic to cross into another country's own top-10 is inherently a hard bet even widened to several target markets at once — most real predictions will still resolve INCORRECT. `accuracy_pct` is `null` until at least one prediction has been evaluated, and is never padded or estimated. Items awaiting a graded check are deliberately excluded from `accuracy_pct` until the relay finalizes them, so the number never reflects an incomplete check.
